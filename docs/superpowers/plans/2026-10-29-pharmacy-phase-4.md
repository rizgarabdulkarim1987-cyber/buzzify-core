# Pharmacy phase 4: suppliers, purchase orders, receiving against orders, supplier invoices, payables, supplier returns and credit notes

Binding design: `docs/superpowers/specs/2026-10-27-pharmacy-design.md` (4.3 purchasing tables, 4.4 money, 4.5 permissions, 5 screen 7, 12 row 4). Phase 2 plan (receipts and stock), phase 3 plan (idempotency, lock-order and replay lessons).

Acceptance (spec 12 row 4): quantity ordered != received != invoiced (each tracked separately and independently queryable); the supplier statement matches the records (invoices - payments - credit notes = balance, and equals the sum of the open invoice balances).

Brainstorming was run short (owner: "finish all the phases"). My calls are rulings, recorded in the ledger and in the owner report with cost if wrong.

## Rulings for this phase

- R4-1 `PhSupplier` is business-wide (not branch-scoped): name (unique per restaurant, case-insensitive), phone, contact person, address note, default currency (IQD/USD), payment terms in days (0 = on delivery), `active`, note. Archive, never delete. Phase 2's free-text `PhReceipt.supplierName` stays for old rows; a receipt may now also carry `supplierId` (nullable FK, additive). Cost if wrong: none (nullable).
- R4-2 Purchase order (`PhPurchaseOrder` + `PhPurchaseOrderLine`): one branch, one supplier, ONE currency (the order's); statuses `DRAFT -> ORDERED -> PARTIAL -> RECEIVED -> CLOSED`, plus `CANCELLED` (only from DRAFT or ORDERED with nothing received). `CLOSED` is a manual "stop waiting for the rest" with a reason, allowed from ORDERED/PARTIAL/RECEIVED. Number per branch per UTC day `PO-YYYYMMDD-000123`, assigned when ordered, under an advisory lock like receipts. Lines carry `qtyOrdered`, `bonusOrdered`, `unitCostMinor` (price agreed per unit of `unitId`), no tax/discount fields (v1). Editing is allowed only in DRAFT; after ORDERED a change is a new order or a close (history stays true). Cost if wrong: an amend-order feature later.
- R4-3 Receiving against an order reuses the phase-2 receipt (no second receiving path): `PhReceipt.purchaseOrderId`, `supplierId` and `PhReceiptLine.purchaseOrderLineId` (all nullable, additive). On CONFIRM the PO line's `receivedQty`/`receivedBonus` (counters on the PO line, changed only in the purchasing service under the PO row lock) grow and the PO status moves PARTIAL/RECEIVED. Over-receipt (received > ordered, bonus separately) is refused `OVER_RECEIPT`; the way to take more is to receive without an order or to raise a new order. Receiving a product not on the order against it is refused `NOT_ON_ORDER`. A CANCELLED/CLOSED order cannot be received against. The receipt's unit cost may differ from the order's: it is stored as received (the batch cost is what the receipt says) and the difference is shown, never blocked. Cost if wrong: a tolerance setting.
- R4-4 Supplier invoice (`PhSupplierInvoice` + `PhSupplierInvoiceLine`): supplier, invoice number, invoice date, due date (default date + supplier terms), currency, lines referencing CONFIRMED receipt lines (`receiptLineId`, `qtyInvoiced`, `unitCostMinor`, `lineTotalMinor`), plus a signed `adjustmentMinor` (freight, discount; needs a reason text). `totalMinor = sum(lines) + adjustment` stored and CHECKed. Invoiced quantity per receipt line may not exceed received (qty + bonus counted as received; bonus is invoiced at zero cost or not at all: `qtyInvoiced <= qty + bonus`) minus already invoiced, in sum across invoices (`INVOICE_EXCEEDS_RECEIVED`, guarded by locking the receipt line's counter). Duplicate prevention (feeds phase 5): `UNIQUE (restaurantId, supplierId, number)` and `fingerprint = sha256(supplierId|number normalised|date|currency|totalMinor)` unique per restaurant; a second entry is refused `DUPLICATE_INVOICE` and points at the first. The invoice cost never rewrites the batch cost (batch cost = receipt's); the variance (invoice vs receipt vs order) is a query, not a mutation. Cost if wrong: a re-costing action.
- R4-5 Payable = the invoice itself: `paidMinor` and `creditedMinor` are counters on the invoice with `CHECK (paidMinor + creditedMinor <= totalMinor)`, changed only in the payments service under the invoice row lock; `balance = total - paid - credited`. Status derived and stored: OPEN, PARTIAL, PAID, VOID (void only when nothing paid or credited, with reason, and it releases the invoiced quantities). No separate `PhPayable` table (single source of truth). Cost if wrong: none.
- R4-6 Supplier payment (`PhSupplierPayment` + `PhSupplierPaymentAllocation`): supplier, currency, method (CASH, TRANSFER_MANUAL, CHEQUE_MANUAL, CARD_MANUAL), amount, paid-on date, reference text, clientKey; the amount must be fully allocated to invoices of the same supplier AND currency (no advances, no cross-currency; `UNALLOCATED`/`CURRENCY_MISMATCH` refused). Allocation never exceeds an invoice's balance (guarded update + CHECK). Supplier payments do NOT touch the cashier drawer or shifts (paid from the office); cost if wrong: add a PAID_OUT cash movement in phase 7. A payment is never edited or deleted: a mistake is a reversal row (`PhSupplierPayment.reversesId`, once) that restores the balances.
- R4-7 Supplier return (`PhSupplierReturn` + lines) and credit note: a return takes stock from a batch's `available` or `quarantine` bucket of the branch (movement type SUPPLIER_RETURN through `applyMovement`), reason required, supplier must be the batch's supplier-of-record only if known (not enforced: phase-2 ruling "supplier not in batch identity"). A return is created CONFIRMED in one transaction (no draft). The credit note (`PhCreditNote`) is a separate document recorded when the supplier agrees: supplier, currency, number (supplier's own, unique per supplier), amount, date, optional `supplierReturnId`, `appliedMinor` counter with CHECK `<= amountMinor`; applying a credit note to an invoice is an allocation row (`PhCreditAllocation`) that raises the invoice's `creditedMinor` (same guarded update). A credit note's currency must equal the invoice's. Cost if wrong: refund-from-supplier (cash back) flow is not built; the credit offsets future invoices only.
- R4-8 Statement (`ph.suppliers.statement`): per supplier, per currency, for a date range: opening balance, then chronological rows (invoice +, payment -, reversal +, credit note -, applied credit not double counted: credit notes reduce the balance when recorded, allocation only maps them), closing balance. Invariant tested: closing balance = sum of open invoice balances - unapplied credit = recomputed from raw rows. Hand-figure tests. Cost gating: needs `purchase.manage` and `cost.view`.
- R4-9 Permissions: everything in this phase needs `purchase.manage` (OWNER, BRANCH_MANAGER, PHARMACIST_IN_CHARGE, ACCOUNTANT and STOCK hold it, as the code matrix says; correction R4-9a: recording or reversing a supplier payment, voiding an invoice and applying credit ALSO need report.view, which STOCK lacks) and monetary figures need `cost.view` for read actions. No new permission keys (the matrix test is unchanged). Voiding an invoice and reversing a payment additionally need `report.view` (a second pair of eyes is NOT enforced; recorded). Cost if wrong: a dedicated `payable.manage` key.
- R4-10 Idempotency and replay: every create (supplier, PO, invoice, payment, return, credit note) takes a `clientKey`, unique per restaurant; a replay compares branch/user/payload hash and returns the stored row or `CLIENT_KEY_MISMATCH` (phase-3 lesson). UI uses per-attempt keys by signature, persisted with the draft.
- R4-11 Lock order (documented in a header comment of the purchasing services): client-key advisory lock (7201 namespace) -> PO row FOR UPDATE -> receipt line counters -> invoice rows FOR UPDATE (ordered by id) -> stock rows (existing phase-2/3 order, batchId COLLATE "C") -> number lock (7202). Two-int advisory keys only.
- R4-12 Tenant/branch isolation: PhSupplier, supplier invoices, payments, credit notes are business-wide (restaurantId only, any `purchase.manage` holder at any branch of the business sees them); PO, supplier return are branch-scoped (`branchId` NOT NULL, composite FK, in `PHARMACY_BRANCH_SCOPED_MODELS`). The client never supplies restaurantId/branchId except through the validated place. Audit logs carry ids, counts, statuses and amounts, never free text notes or phone numbers.
- R4-13 No AI, no scanning of invoices (phase 5), no supplier portal, no automatic reorder suggestion (phase 7 assistant), no tax. Reorder hints: the PO new-order screen may pre-fill from products below `minQty` (read-only query, existing `PhProductBranch.minQty`); cost if wrong: none.
- R4-14 UI: no motion; en/ar/ckb (ar/ckb machine-drafted); RTL logical CSS; 375/768/1280 without horizontal scroll; axe clean; every state text plus icon; targets >= 44px; `impeccable` then `21st-ui-build`; drafts kept on the device with a leave guard; the screens live under `/pharmacy/purchasing/**` with nav entries in the pharmacy shell only (never `src/studio/nav.ts`).
- R4-15 Tests share ONE database: one test file at a time, always `BUZZIFY_DB_PORT=54503`.
