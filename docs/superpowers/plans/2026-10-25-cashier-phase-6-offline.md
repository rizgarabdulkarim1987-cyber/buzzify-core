# Cashier phase 6: offline work (inside Core)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (inline). Steps use checkbox (`- [ ]`) syntax.

**Goal:** A cashier keeps selling when the network drops. On the device, opening a table, adding lines, sending to the kitchen, asking for the bill, cancelling an order and taking **cash** go into a durable IndexedDB queue; each operation carries a client-made `operationId` and the order `expectedVersion` it was made against. When the network returns, the queue is replayed in order through `POST /api/pos/sync`. The server runs every operation **exactly once** (a second send of the same `operationId` changes nothing and answers the stored result), decides every conflict, and never applies or drops one silently.

**Architecture:** A new table `PosSyncOperation` (unique `(restaurantId, operationId)`) is claimed and completed **inside the same transaction** as the change it records: `runAction` (the Studio framework) takes an optional `operation` and, for the action's one `ctx.transaction`, inserts the claim first, stores the transaction's return value as `result` last, and queues a `pos.sync.apply` audit row. So `pos.openOrder`, `pos.addLine`, `pos.sendToKitchen`, `pos.requestBill`, `pos.cancelOrder` and `pos.payOrder` keep their permission, gate, tenant scope, audit and version checks unchanged; the route is a thin loop over `runAction`. The device side lives in `src/lib/pos-sync/` (raw IndexedDB store, queue, a pure replay engine, a pure local-state reducer, guards), tested against `fake-indexeddb`. A hand-written service worker `public/pos/sw.js` (scope `/pos/`) caches static assets and one data-free shell page, `/pos/offline`; it caches no API response and no other HTML.

**Spec / source:** `docs/superpowers/plans/2026-10-24-cashier-unified-plan.md` (phase 6; "server stays the authority on order state", spec 17), the frozen cashier plan `buzzify-restaurant/docs/superpowers/plans/2026-10-24-cashier-6-offline.md` (the behaviour; this plan re-points it at Core's Studio-framework actions and trims it), and the real code of phases 3-5.

## Rulings

1. **Allowed offline** (`OP_KINDS`): `openOrder` (dine-in, on a table the cache shows free), `addLine`, `sendToKitchen`, `requestBill`, `cancelOrder`, `payCash`. Nothing else is queueable; anything else is refused by the schema. **Online only** (hidden on the offline screen): shifts, expenses, takeaway/delivery orders (customer data and queue numbers belong to the server), moving a table, line edits/discounts, fulfillment, QR requests, kitchen screen, setup, reports. Out of scope this phase: merging a table opened on two devices (the second `openOrder` answers `tableOccupied`), device-to-device sync, background-sync events.
2. **One action per kind, no new business code.** `OP_ACTIONS` maps a kind to its existing `ActionDef`; the op payload is that action's input minus `orderId`/`expectedVersion`'s server-side parts. The server never trusts a client price: `addLine` prices from the live catalog at replay; `payCash` carries `expectedTotal` (the total the cashier saw), so a price or rate change meanwhile answers `totalChanged` with nothing taken.
3. **Operation shape:** `{ operationId: uuid, kind, deviceId: uuid, clientAt: ISO, orderRef: {id} | {op: uuid}, payload }`. `{op}` is an order opened by an earlier operation of the same restaurant; only the server resolves it, from that operation's stored `result.orderId`. Unknown ref → `unknownRef`.
4. **Versions:** every queueable action bumps `PosOrder.version` by exactly one (pinned by a test). An op queued offline stores `expectedVersion = cached version + earlier queued ops on that order` (an order opened offline starts at 1). Replay sends it unchanged, so a change from another device is `stale`, never overwritten.
5. **Exactly-once:** `PosSyncOperation` holds `{restaurantId, userId, deviceId, operationId, kind, payloadHash, result Json, clientAt, appliedAt}`. A stored `operationId` with the same hash and user answers `done, replayed: true` with the stored result and runs nothing; the same id with another hash/user is `operationMismatch`/`wrongActor`. A failed action stores nothing (the claim rolls back with it), so a fixed retry may reuse its id. Two concurrent sends of one id: the unique index lets one commit; the loser re-reads and answers the stored result.
6. **Conflict policy, server wins:** answer codes `stale` (with `currentVersion`), `locked` (with `orderStatus`: paid/cancelled/rejected elsewhere), `totalChanged`, `tableOccupied`, `shiftRequired`, `productUnavailable`, `forbidden`, `invalid`, `operationMismatch`, `wrongActor`, `unknownRef`, `failed`. The first failing op of an order sets it `attention`; later ops of that **same order** are `blocked` (in the batch they answer `skipped`); other orders keep replaying. The cashier resolves an attention op in the queue panel: **Retry** (same op, after an outside fix such as opening a shift), **Apply to current order** (only `stale`: re-send at the server's `currentVersion`, later ops of the order shifted by the same delta), **Discard** (online only, confirm; a `payCash` also needs a typed reason because cash was taken; posts the audit action `pos.sync.discard` first). Nothing resolves itself.
7. **Time:** every server timestamp is server time at sync (`paidAt`, `sentAt`, `seatedAt`); `clientAt` is metadata (stored, and in the `pos.sync.apply` audit row). An offline sale lands in the Baghdad day it was synced and in the cashier's open shift **at that time** (`lockOpenShiftOf`); none → `shiftRequired`.
8. **Session and staleness:** the cached snapshot is stored per scope `restaurantId:userId`. New ops are accepted while the snapshot is younger than `OFFLINE_MAX_AGE_MS = 12 h`; after that the screen is read-only and keeps the queue. A 401 pauses replay (`signedOut`) and resumes after sign-in as the same user. The queue is never sent under another user (`wrongActor` server side, scope key client side). Sign-out warns when the scope holds waiting ops, never deletes the queue, and deletes that scope's snapshot.
9. **What the queue may hold:** only action inputs, ids, device id and times. Never cookies, tokens, passwords. `done` ops drop their payload and are pruned after 24 h.
10. **Transport:** a Route Handler (Server Action ids change per build, and an old cached shell must still sync). `POST /api/pos/sync` `{ deviceId, operations: 1..25 }` → `{ serverTime, answers }`; `GET /api/pos/sync/snapshot` → the read cache; `POST /api/pos/sync/discard`. All require a session (401), same origin (403), JSON (415/400), body ≤ 256 KB (413), `Cache-Control: no-store`. The till permission and the live Cashier subscription are checked by the actions and the snapshot query themselves.
11. **Service worker:** `public/pos/sw.js`, scope `/pos/`, registered by the till layout. `/_next/static/*` cache-first; navigation to `/pos/offline` network-first with cache fallback; any other `/pos/**` navigation that fails (offline) answers the cached `/pos/offline`; `/api/*` and every other response are never cached. Studio pages are outside the scope. The shell page holds no restaurant data (it is a client component that reads IndexedDB).
12. **Provisional numbers:** an order opened offline shows `P-<deviceTag>-<n>` until it syncs, then the server number. The offline "receipt" is the kitchen/bill view with the heading "Provisional: final number after sync"; the real receipt is the server's `/pos/orders/[id]/receipt`.

## Review Focus

1. A cash payment replayed twice (response lost, two tabs, retry from the panel): one `PosPayment`, one `pos.payment.take` audit row, same stored answer (Tasks 1, 2).
2. Another device cancelled/paid/changed the order while this one was offline: the op stops with a clear reason, later ops of that order are blocked, other orders keep syncing, nothing silent (Tasks 2, 3, 6).
3. Money: the offline total equals the server's total for the same lines (tax, service, 100% invoice discount); a rate/price change meanwhile is `totalChanged` with both amounts, never a different charge (Tasks 4, 2).
4. A queue that outlives its context: session expired, another user on the same device, snapshot older than 12 h, shift closed elsewhere: never sent as the wrong person, never lost, screen read-only rather than selling on stale data (Tasks 2, 3, 5, 6).
5. Another restaurant's operation ids, orders and snapshot are unreachable in both directions (Tasks 1, 2).
