# Pharmacy phase 2: stock, batches, manual receiving, counts, expiry alerts

Binding design: `docs/superpowers/specs/2026-10-27-pharmacy-design.md` (sections 4.3, 4.4, 5 screens 4-5, 12 row 2).
Acceptance (spec 12): no negative stock (CHECK); a correction is a reversing entry; the 90-day expiry alert equals its query; a count with differences needs an approval.

Brainstorming was run short: the owner approved the design and said "finish all the phases". The calls below are mine, recorded as rulings in the ledger (`.superpowers/sdd/.../progress.md`).

## Rulings for this phase

- R2-1 Receiving in phase 2 is a plain receipt (`PhReceipt` + `PhReceiptLine`), with the supplier as free text. Phase 4 adds `PhSupplier`, purchase orders and invoices and links the receipt then. Cost if wrong: one nullable FK added in phase 4.
- R2-2 Stock is held per `(batch, branch)` in four whole-number buckets of the base unit: `available`, `reserved`, `quarantine`, `damaged`, each `CHECK >= 0`. Money is `BigInt` minor units plus `currency`. The batch stores `unitCostMinor` for one `costUnitId` (the unit it was bought in), never a per-base fraction (spec 4.4). Cost if wrong: a reporting helper.
- R2-3 `PhStockMovement` is append-only (a DB trigger refuses UPDATE and DELETE). A correction is a new movement with `reversesId` set to the original; one movement can be reversed once (partial unique index on `reversesId`). Cost if wrong: a trigger drop.
- R2-4 A batch is identified by `(restaurantId, productId, lot, expiryDate, supplierName)`; receiving the same lot and expiry again adds to the existing batch. Expiry by month is stored as the last day of the month with `expiryPrecision = MONTH`.
- R2-5 Sellable stock excludes `reserved`, `quarantine`, `damaged`, an expired batch (`expiryDate < today`) and a batch whose status is not ACTIVE. A helper `sellableStock` is the single definition used by phase 3.
- R2-6 Receiving and adjusting need `stock.adjust`/`purchase.manage` (receive: `purchase.manage` or `stock.adjust`); counting needs `stock.count`; approving a count with differences needs `stock.adjust` and a reason, and the approver may not be the person who counted when the pharmacy has more than one user with the permission (otherwise allowed, recorded). Cost if wrong: one rule.
- R2-7 The expiry alert horizon is 90 days by default (`PhSettings.expiryAlertDays` is NOT added; the page takes a `days` parameter of 30/60/90/180). A batch that is already expired with stock left is listed first under "expired". Expiry follow-up (`PhExpiryAction`: NEW, IN_PROGRESS, MOVED, DISPOSED, RETURNED, with assignee and note) is a status row per `(batch, branch)`; disposing writes a DAMAGE movement.
- R2-8 Time in expiry maths is by calendar day in UTC (the pharmacy has no timezone setting yet). Cost if wrong: an alert one day off near midnight.
- R2-9 Carry-forwards done here: the second-person rule for support consent (a Super Admin may not record consent naming themselves), phGate reads `Application(pharmacy).status` (kill switch: DISABLED/ARCHIVED closes `/pharmacy`), stale PREVIEW import/price batches are cancelled on read of the list after 7 days, `archived products out of default bulk pricing scope`. Each is a small task below.
- R2-10 The "typo-tolerant search" exception is NOT built; recorded as an open owner decision.
- R2-11 No motion anywhere in the pharmacy screens: no `transition`, no `animation`, no `@keyframes`, no framer-motion (a test scans `src/app/pharmacy` and fails on them). `prefers-reduced-motion` is not used as a loophole.

## Tasks

Each task: tests first (TDD), implementation, `npm run typecheck`, `npx eslint` on touched files, commit with the trailer.

1. **Schema + migration** `prisma/migrations/20261027160000_pharmacy_stock`: enums `PhBatchStatus` (ACTIVE, RECALLED, BLOCKED), `PhExpiryPrecision` (DAY, MONTH), `PhMovementType` (RECEIPT, SALE, RETURN_IN, RETURN_QUARANTINE, ADJUST, DAMAGE, TRANSFER_OUT, TRANSFER_IN, SUPPLIER_RETURN, COUNT, QUARANTINE_RELEASE), `PhStockBucket` (AVAILABLE, RESERVED, QUARANTINE, DAMAGED), `PhReceiptStatus` (DRAFT, CONFIRMED, VOID), `PhCountStatus` (OPEN, SUBMITTED, APPROVED, CANCELLED), `PhExpiryStatus`. Models: `PhBatch`, `PhStockBalance`, `PhStockMovement`, `PhReceipt`, `PhReceiptLine`, `PhStockCount`, `PhStockCountLine`, `PhExpiryAction`. All carry `restaurantId`; `branchId` NOT NULL with composite FK to `Branch(restaurantId, id)` on balance, movement, receipt, count, expiry action; composite FKs to the product/unit/batch. CHECK constraints (raw SQL in the migration), the append-only trigger, the unique partial index on `reversesId`. Register in `RESTAURANT_SCOPED_MODELS` and `PHARMACY_BRANCH_SCOPED_MODELS` (PhBatch is business-wide, not branch-scoped); replace the empty `PH_STOCK_RECORD_MODELS` guard. Tests: `tests/pharmacy/stock-schema.test.ts` (CHECK refuses negative, trigger refuses update/delete of a movement, one reversal per movement, migration additive guard stays green, registry test green).
2. **Pure stock domain** `src/server/domain/pharmacy/stock.ts` + `expiry.ts`: `toBase(qty, unit)`, month expiry normalisation, `isExpired(batch, today)`, `daysToExpiry`, `sellableStock(balance, batch, today)`, FEFO order (earliest expiry, then lot, then id; MONTH expiry counts as end of month), expiry bands (expired, within 30/60/90). Property-style tests for conversions and bounds (max safe integers, BigInt money).
3. **Stock service** `src/server/pharmacy/stock.ts`: `applyMovement(tx, input)` is the only writer of balances: conditional atomic update `UPDATE ... SET bucket = bucket + $d WHERE id AND bucket + $d >= 0`, creates the balance row on first use (upsert with `ON CONFLICT`... through the scoped client), writes the movement, returns the new balances. `reverseMovement`. Concurrency test: N parallel decrements on the last unit, exactly one succeeds, none negative, no deadlock (fixed lock order by batch id). Reversal twice refused.
4. **Manual receiving**: actions `ph.stock.receipt.create` (draft, with lines), `.update`, `.confirm` (one transaction: batches upserted by R2-4, movement RECEIPT per line, receipt CONFIRMED; idempotent by `clientKey`), `.void` (before confirm only; after confirm a correction is an adjustment). Queries `ph.stock.receipt.list/get`. Cost visible only with `cost.view`.
5. **Adjustments and quarantine moves**: `ph.stock.adjust` (reason required, bucket-to-bucket or +/-), `ph.stock.reverse`, `ph.stock.damage`, `ph.stock.quarantineRelease`. Queries: `ph.stock.balances` (per product, per branch, with batches, FEFO order, sellable total), `ph.stock.movements` (paged, product/batch filter).
6. **Counts**: `ph.stock.count.open` (scope: whole branch, a category or a shelf location; optional blind count), `.record` (counted qty per batch), `.submit`, `.approve` (differences become COUNT movements, needs `stock.adjust` + reason when any difference exists, R2-6), `.cancel`. Query `.get`/`.list` with expected hidden while blind and the counter is still counting.
7. **Expiry alerts**: query `ph.stock.expiry` (bands, days param, branch scope, only batches with stock in sellable buckets or quarantine), actions `ph.stock.expiry.setStatus`. Test: result equals an independent SQL count for the 90-day horizon (the acceptance test).
8. **Carry-forwards** (R2-9): consent second-person rule, phGate application status, stale PREVIEW cancel, archived out of bulk scope. Each with a test; golden FOOD tests stay green.
9. **Screens** (`impeccable` then `21st-ui-build`; no motion): `/pharmacy/stock` (balances with batch strip and status chips), `/pharmacy/stock/receive` (receipt form with line entry, draft kept on device, leave guard), `/pharmacy/stock/expiry`, `/pharmacy/stock/counts` and `/pharmacy/stock/counts/[id]`, movements list. en/ar/ckb strings, RTL logical CSS, every state has text plus an icon, 375/768/1280 without horizontal scroll, axe clean. Nav entries for the stock section in the pharmacy shell only (not the Studio nav).
10. **Isolation re-test + search latency**: extend the tenant registry and cross-tenant sweep tests to the new models; branch 1 user cannot see branch 2 stock; reuse the resolved actor and gate inside one request (`cache()`), with a test that counts queries for one search before and after; re-run the rule-8 regex test with new receivers (`scoped`, `tx`).
11. **Acceptance test** `tests/pharmacy/acceptance-phase-2.test.ts` (spec 12 row 2), README update, ledger update, whole-phase review on the most capable model, full suite + typecheck + eslint green.
