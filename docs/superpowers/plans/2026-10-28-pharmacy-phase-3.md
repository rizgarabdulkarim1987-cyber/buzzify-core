## Rulings for this phase

- R3-1 One currency per sale (IQD or USD, spec 15.2). Question D is assumed answered "USD is for pricing and purchasing only": a sale and all its payments are in the sale's currency. Mixed-currency payment (with a recorded exchange rate) is NOT built; cost if wrong: a payment-method extension in phase 7.
- R3-2 Every sale line stores its OWN price at sale time (`unitPriceMinor`, `unitId`, `priceId` of the price row used), so a later price change never rewrites history (phase-2 carry-forward). A line whose unit has no open price in the sale's currency at that branch cannot be sold (`NO_PRICE`). A manager may override a price only with `price.change` plus a reason.
- R3-3 Allocation is FEFO per line through `allocateFefo` and `applyMovement` type SALE (one movement per allocation, `refType='sale'`, `refId=sale line allocation id`). Only `available` in ACTIVE, not-expired batches is allocated. A batch override (`batch.override` permission + reason) picks a specific sellable batch. Expired, recalled, quarantine, reserved and damaged stock is never allocated.
- R3-4 Rx levels: OTC sells to anyone with `shift.use`. RX needs a holder of `rx.dispense` as the selling user (CASHIER cannot), the pharmacist's id is stored on the line. RESTRICTED (controlled drugs) cannot be sold in phase 3 at all (`RESTRICTED_NOT_AVAILABLE`): the controlled register and prescriptions arrive in phase 7; cost if wrong: the owner cannot sell a controlled drug until phase 7 (this is the safe default).
- R3-5 Invoice rounding is an explicit setting on `PhSettings` (`roundingStepMinor`, default 0 = none; IQD 25/50/250/1000 allowed) applied to the invoice total, never to lines; the difference is stored on the sale (`roundingMinor`, signed). Discounts: per line (amount or percent) and per invoice; need `discount.apply` up to `PhSettings.maxDiscountPercent` (default 5), above that `discount.over_limit` + reason. A discount never takes a line below cost-free zero (total >= 0).
- R3-6 Payments in phase 3: CASH only, plus `CARD_MANUAL` and `TRANSFER_MANUAL` recorded manually (no gateway, owner decision); change is computed and stored for cash. A sale is created paid in full (or as a hold). Credit sales are phase 7.
- R3-7 Idempotency: `PhSale.clientKey` unique per restaurant; a repeat returns the stored sale; `PhPayment.clientKey` likewise. Sale numbers are per branch per UTC day `YYYYMMDD-000123`, assigned under a per-branch advisory lock like receipts.
- R3-8 Shifts: one OPEN shift per user per branch. A sale needs an open shift of the selling user. Close: counted cash vs expected (opening float + cash payments - cash change - cash refunds +/- cash movements), variance stored, a variance over `PhSettings.shiftVarianceLimitMinor` needs `report.view`-holder approval (BRANCH_MANAGER/OWNER/PIC) with reason. A shift with unresolved holds can close (holds are branch-level and expire after 24 h).
- R3-9 Returns reference a sale line allocation; limit = sold - already returned; the units go to QUARANTINE (movement RETURN_QUARANTINE, spec 4.4) and become sellable only through the existing quarantine release (phase 2). `return.approve` permission required (CASHIER cannot return, a cashier requests nothing in phase 3). Refund is cash/manual in the original currency and is recorded as a cash movement of the current shift. A sale older than 30 days needs OWNER/BRANCH_MANAGER (setting `returnWindowDays`, default 30).
- R3-10 Cancel of a whole sale = a full return of all lines by an approver (no delete, no edit).
- R3-11 Receipts: browser print is the base (spec 8). A receipt payload is rendered from the stored sale (never from the screen), 80 mm and 58 mm templates, RTL aware, with a "copy" marker on reprints; every reprint writes `PhReceiptReprint`. Silent printing, ESC/POS and the cash drawer remain separate integrations (not built). Print failure is a UI state only.
- R3-12 Scanner: keyboard-wedge capture (<= 50 ms between characters + Enter/Tab terminator), barcode is always a string (leading zeros kept), test screen showing what was received. Camera scanning is NOT built.
- R3-13 No offline selling (spec 11). If the network fails the screen says so and keeps the cart on the device; the sale is not queued.
- R3-14 No motion; same UI rules as phase 2 (impeccable then 21st-ui-build, en/ar/ckb with ar/ckb machine-drafted, RTL logical CSS, 375/768/1280, axe, text+icon states, 44px targets).
- R3-15 Tests share ONE database: one test file at a time, always `BUZZIFY_DB_PORT=54503`.

## Tasks

Each task: tests first (real RED output saved), implementation, typecheck, eslint on touched paths, small commits with the trailer, independent reviewer per task, scoped re-review (or controller read with evidence) after fixes.

1. **Schema + migrations** (`20261028100000_pharmacy_sales`): enums PhSaleStatus (HELD, COMPLETED, VOID_BY_RETURN? no: COMPLETED, RETURNED_PARTIAL, RETURNED_FULL, HELD, EXPIRED_HOLD), PhPaymentMethod (CASH, CARD_MANUAL, TRANSFER_MANUAL), PhShiftStatus (OPEN, CLOSED), PhCashMovementType (FLOAT_OPEN, SALE_CASH, CHANGE_OUT, REFUND_CASH, PAID_IN, PAID_OUT, FLOAT_CLOSE_ADJUST); models PhShift, PhCashMovement, PhSale, PhSaleLine, PhSaleLineAllocation, PhPayment, PhSaleHold (or HELD status on PhSale with a heldUntil), PhReturn, PhReturnLine, PhReceiptReprint; additive columns on PhSettings (`roundingStepMinor`, `maxDiscountPercent`, `shiftVarianceLimitMinor`, `returnWindowDays`) with defaults (ALTER on an existing table: ADD COLUMN with DEFAULT, keep it a metadata-only change). Money BigInt + currency; CHECKs (qty > 0, totals >= 0, paid >= total for COMPLETED, returned qty <= sold qty by a trigger or a guarded update); composite FKs for tenant/branch/product/unit/batch; unique (restaurantId, clientKey) on sale and payment; register models in the tenant registries; update the stock `refType` conventions. Tests: constraints, FKs, registry, additive guard.
2. **Pure sales domain** `src/server/domain/pharmacy/sale.ts`: line totals (qty x unit price, line discount amount/percent with integer maths, floor/round rule stated), invoice discount distribution (largest remainder so lines sum exactly), invoice rounding with signed difference, payments validation (cash change, non-cash exact), permission thresholds, return limits, expected cash. Property tests with BigInt extremes.
3. **Sale service + actions** (`sales.ts`, actions/queries): `ph.sales.create` (idempotent, one transaction: price lookup at now, FEFO allocation, SALE movements, payment rows, number assignment, shift cash movement), `ph.sales.hold` / `resume` / `discardHold`, `ph.sales.get`, `ph.sales.list`; concurrency test (N parallel sales of the last unit -> one wins); batch override; Rx rules; RESTRICTED refusal; price override; discount thresholds; cost snapshot per allocation (`unitCostSnapshotMinor` from the batch cost per unit when the sold quantity is a whole multiple of the cost unit, else the proportional line cost computed with integer division stored as `costSnapshotMinor` for the allocation's quantity: decide and document); cost gating.
4. **Shifts and cash**: `ph.shifts.open/close/current`, `ph.cash.paidIn/paidOut` (reason, permission), shift report query (sales count/total by method, returns, cash expected, variance), approval for variance, one open shift per user per branch (partial unique index).
5. **Returns**: `ph.returns.create` (by sale, lines, qty, reason, refund method), limits, quarantine movements, cash refund movement, window rule, `ph.sales.cancel` as a full return; queries for returnable lines.
6. **Receipts and printing data**: receipt payload builder (from stored data), 80/58 mm HTML templates with print CSS (`@page`), reprint action + log, golden snapshot tests for 58/80 in Arabic and English, print failure never changes sale state.
7. **Scanner capture**: pure TS capture machine (`src/app/pharmacy/_ui/scanner.ts`) with injectable clock, hook, scanner test screen (`/pharmacy/settings/devices`), unknown/multi-match flows served by the existing barcode resolution queries; unit tests with simulated key streams (fast burst vs typing, Arabic digits, leading zeros, Enter/Tab, stray characters, duplicates).
8. **Sale screen UI** `/pharmacy/sell` (invoke `impeccable` then `21st-ui-build`): central search/scan, results grid with strength/form/pack, cart with qty/unit change/discount, batch strip (FEFO with expiry and override), hold/resume, pay dialog (cash tendered/change, manual card/transfer), receipt view + print button, shortcuts F2/F4/F8/Esc, touch mode >= 44px, offline state, draft cart on device, shift gate (open shift first).
9. **Shifts / returns / sales list UI**: `/pharmacy/shifts` (open/close/report), `/pharmacy/sales` (list, detail, reprint, return), `/pharmacy/returns` flow.
10. **Isolation + latency**: extend the isolation sweep to all phase-3 definitions, rule-8 for sale tables written only by the sales/return services, query-count test for the sale path.
11. **Acceptance + README + whole-phase review**: `tests/pharmacy/acceptance-phase-3.test.ts` for spec row 3, README (phases 0-3), ledger, whole-phase review (Opus), full suite + typecheck + eslint.
