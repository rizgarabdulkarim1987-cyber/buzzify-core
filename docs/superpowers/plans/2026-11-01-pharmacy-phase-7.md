## Rulings

- R7-1 Controlled drugs (`rxLevel = RESTRICTED`): a sale line of a RESTRICTED product needs (a) the seller holds `rx.dispense`, (b) a complete prescription record attached to the sale (R7-2), (c) quantity within the product's `maxDispenseQty` (new nullable column on PhProductBranch is NOT added: a per-business setting `controlledMaxQty` in PhSettings, default 30 base units, owner-editable, 0 = no limit). Each dispensed unit is written to an append-only controlled register (`PhControlledEntry`, one row per sale line allocation batch) in the same transaction as the sale; a return of a controlled line writes a reversing register row and the units go to QUARANTINE as for any return (existing rule). The register is never updated or deleted by any code path (enforcement rule + test). RESTRICTED stays unsellable when the business has `controlledEnabled = false` (default false): the refusal `RESTRICTED_NOT_AVAILABLE` remains the default so existing behaviour is unchanged until the owner switches it on. Cost if wrong: a flag and a limit value; the register rows already written stay valid.
- R7-2 Prescription record `PhPrescription` (business + branch scoped): `number` (text, what the paper says), `prescriberName`, `prescriberLicense?`, `patientName` (required for RESTRICTED, optional for RX), `patientIdNote?` (document type + last 4 characters only, never a full ID number: ruling), `issuedOn` (date, not future, not older than 30 days for RESTRICTED, 180 for RX), `saleId` (set when the sale completes), optional attachment. Patient fields and prescriber fields NEVER enter `AuditLog.changes`, logs, exports, reports or the assistant; audit rows carry ids, counts and statuses only. A prescription is single-use per sale (unique saleId); a RESTRICTED prescription number cannot be reused within the business for the same product within its validity window (`DUPLICATE_PRESCRIPTION`). Cost if wrong: relaxing a unique index.
- R7-3 Attachment: image/PDF up to 5 MB stored through the existing private storage module (phase 5 `intake/storage.ts` pattern, never a public URL), referenced by `PhRxAttachment` (storage key, mime, size, sha256). Upload needs `rx.dispense`; reading bytes needs `rx.attachment.view` checked server-side on every read through a route handler that streams the bytes with `Cache-Control: private, no-store`; a read is audited (counts only: attachment id, who). Support actors never read it. Cost if wrong: a permission name.
- R7-4 Retention: `PhSettings.rxRetentionDays` default 3650 (10 years) as a SAFE default because owner question B is unanswered; nothing is purged by this phase (no deletion code path); the setting and the open question are stated in the README and the owner report. Cost if wrong: a purge job later plus a number.
- R7-5 Credit sales: new `PhCustomer` (name, phone (private), `creditLimitMinor` + `currency`, active, note); a sale may be paid on credit to a customer when `PhSettings.creditEnabled` (default false): payment method `CREDIT` (additive enum value) whose amount goes onto the customer's balance in the SAME transaction, under a lock on the customer row, refused when `balance + amount > creditLimit` (`CREDIT_LIMIT_EXCEEDED`) or the customer's currency differs from the sale's (never convert). A credit sale may mix CREDIT with cash/card/transfer payments of the same sale currency; a sale cannot be 100% unpaid without a customer. Credit never touches the cash drawer or the shift cash total. Customer payments (`PhCustomerPayment`, cash/card/transfer manual) reduce the balance, are idempotent by clientKey and payloadHash, can be corrected once by a reversing row (phase 4 supplier-payment pattern), and DO touch the open shift's cash total when paid in cash (phase 3 cash movement `CUSTOMER_PAYMENT`, additive enum value). A refund of a credit sale reduces the balance first (up to the unpaid amount) and refunds the rest by the original methods (existing refund rules). Statements and ageing per customer per currency (never summed across currencies). Customer records are business-wide; the phone is shown only with `customer.manage`. Needs new permissions `customer.manage` (OWNER, BRANCH_MANAGER, PHARMACIST_IN_CHARGE, ACCOUNTANT) and `credit.sell` (same plus CASHIER? no: PHARMACIST and above); no existing role changes except additions. Cost if wrong: permission membership; one flag.
- R7-6 Assistant: six tools only (`batches_expiring`, `stock_below_reorder`, `slow_movers`, `transfer_candidates`, `unpaid_supplier_invoices`, `margin_change`) as TypeScript read functions over the existing scoped services (no free SQL, no new SQL surface beyond one aggregate for slow movers), each with a zod input/output shape (`tool-shapes.ts`), each gated like the equivalent report (`report.view`, cost tools need `cost.view`, margin tool needs `profit.view` too) and branch-limited by the actor's branches. The model only chooses a tool and phrases the answer; `grounding.ts` extracts every number, date and quantity from the answer and refuses (and falls back to the plain tool result table) when any figure is absent from the tool outputs; every answer shows period, branches, `dataAsOf`, supporting links and a fact/estimate label. Prompt-injection: all tool data and any text from the database is passed as data in a delimited block marked untrusted; the model has no write tool; an instruction inside data is ignored (tested with a hostile product name). No patient, customer, prescription or phone data is ever given to the model (whitelist of fields, `redactPhones`). Provider failure, budget exhausted or `ai.use` missing: the screen shows the plain tool result and the sale, stock and alerts are unaffected. Budget: reuses PhAiUsageMonth/PhAiReservation like phase 5, kind `ASSISTANT`. The model is injected (`provider` argument); tests use a scripted mock provider; no real model call is made anywhere in this phase. Demand forecast: only the sentence "insufficient data" unless >= 8 weeks of sales exist, then a seasonal-naive figure labelled "estimate" computed in code (not by the model); never suggests selling expired stock or consuming more of a drug. Cost if wrong: swap the provider and tune prompts; the tool layer stays.
- R7-7 Assistant writes: the assistant can only create a PROPOSAL (`PhAiProposal`: kind TRANSFER|REORDER|SUPPLIER_RETURN, product ids and quantities, `status` PROPOSED|ACCEPTED|DISMISSED) shown on a review screen with the effect spelled out; accepting hands the person to the EXISTING draft creation (transfer request or purchase order draft) pre-filled, and creates nothing else. Cost if wrong: the proposal table can be dropped.
- R7-8 Advanced printing: (a) A4 sale invoice and A4 return slip from the existing receipt data (RTL, Arabic/Kurdish/English, business header, per-line tax-free totals since there is no tax column), (b) shelf label and batch label sheets (product name, strength, batch, expiry, barcode as CODE128 SVG rendered in code, price only when `catalog.view`), 3 sizes (40x25, 50x30, 58 mm wide roll), preview page with `@page` sizes, margins per workstation stored in PhSettings.print JSON (validated), a test-print page, (c) every reprint writes `PhReceiptReprint` (existing) with a copy number. Printing is browser-based (`window.print`), no silent printing, no ESC/POS (separate integration, spec section 8). Printing never changes sale state. Cost if wrong: CSS and a template.
- R7-9 Cash drawer (I-5) is NOT built: it needs a local helper program (spec section 8). Stated open item.
- R7-10 UI: no motion; en/ar/ckb parity (ar/ckb machine-drafted); RTL logical CSS; 375/768/1280 no horizontal scroll; axe clean in EN, AR AND ckb on every new screen and state; targets >= 44px; text AND icon for states; failures through `phMessage`; WriteBlocked read-only mode (assistant answers and statements stay readable; sales, uploads and payments blocked); tables first.
- R7-11 Tests share ONE database: one DB test file at a time, always `BUZZIFY_DB_PORT=54503`. Migrations additive only (enum values added with `ADD VALUE IF NOT EXISTS`; the guard must allow that and nothing else).
