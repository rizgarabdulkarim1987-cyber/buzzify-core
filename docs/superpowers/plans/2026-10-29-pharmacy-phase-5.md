## Rulings

- R5-1 Draft only. Intake never touches stock, price or invoices. Approval creates a DRAFT `PhReceipt` (phase 2/4 `createDraft`, with supplier and lines); an authorised person confirms it on the existing receive screen. The extracted invoice header (number, date, total, currency) is kept on the batch and prefills the phase-4 invoice screen AFTER the receipt is confirmed; the duplicate invoice check (fingerprint + number, phase 4) runs at approval time too. Cost if wrong: none (nothing irreversible happens in intake).
- R5-2 Provider and keys: reuse the gateway as is (`runAi`'s package/provider resolution is cashier-specific, so add `src/server/pharmacy/ai/run.ts` with the same shape but pharmacy tables: `PhAiCall`, `PhAiUsageMonth`, gate = the pharmacy plan's `limits.aiMonthlyBudgetMinor` and a per-restaurant `PhSettings`-free switch: intake is available when the plan budget > 0 and `ai.use` permission). `AI_PROVIDER=fake` stays test/demo only. Cost if wrong: a second gateway wrapper to merge later.
- R5-3 Budget in money, not requests: `aiMonthlyBudgetMinor` is read as USD cents. Cost of a call = tokens x price from env `AI_PRICE_INPUT_USD_MICRO_PER_MTOK` and `AI_PRICE_OUTPUT_USD_MICRO_PER_MTOK` (USD micro-dollars per million tokens; NO default from memory: if unset, intake is refused with `AI_PRICING_NOT_SET`, the safe state). Spend is stored as micro-dollars (BigInt) per Baghdad month. Before a call a worst-case cost (input estimate + max output tokens) is RESERVED with a conditional update (`spent + reserved <= budget`), then settled to the actual cost, so concurrent extractions can never pass the budget; the page that would cross the budget is refused with `AI_BUDGET_REACHED` and manual entry stays open. Cost if wrong: the unit of the plan field (USD cents) may need to be IQD; one conversion.
- R5-4 Files: private storage behind an `IntakeStorage` interface (put, get bytes, signed URL <= 5 min, delete). Production adapter = a SEPARATE PRIVATE R2 bucket (env `PH_INTAKE_R2_ACCOUNT_ID/ACCESS_KEY_ID/SECRET_ACCESS_KEY/BUCKET`, all or none; production without them disables upload with the state `INTAKE_STORAGE_NOT_CONFIGURED`, never falls back to the public media bucket). Dev/test adapter = a local folder outside the repo tree (`os.tmpdir()`), refused in production. Creating the private bucket and its lifecycle rule is an OWNER launch step (listed). Retention 30 days: `purgeExpiredIntakeFiles()` service + script deletes the object and blanks `storageKey` (keeps the sha256 and row data); scheduling is a launch step. Cost if wrong: swapping the adapter.
- R5-5 Limits per file: JPEG/PNG/WebP/PDF, <= 8 MB, <= 10 pages for PDF (counted by parsing the PDF page tree with a tiny pure counter; a PDF whose pages cannot be counted is refused), <= 20 files per batch, total stored bytes of the pharmacy counted against `limits.storageMb`. SHA-256 of the bytes: the same file twice in the business -> the existing file is returned (`DUPLICATE_FILE`, no second stored copy, no second AI call).
- R5-6 Quality gate BEFORE any AI call (saves money): `sharp` metrics on images: Laplacian variance (sharpness), width/height (min 800 px on the short side... threshold constants in one place with the measured rationale), mean luminance and contrast. Below threshold -> status `REJECTED_QUALITY` with the reason codes (`BLURRY`, `TOO_SMALL`, `TOO_DARK`, `LOW_CONTRAST`), "retake" shown. PDFs skip pixel metrics (text/vector) and go straight to the model. Thresholds are constants calibrated on synthetic sharp/blurred renderings of the same page in tests; recalibrate on real photos at UAT (listed). Cost if wrong: a few good photos rejected or blurry ones accepted until calibrated; the reviewer still checks every row.
- R5-7 Extraction: vision model through the gateway (`purpose: 'extract'`), strict JSON schema (spec 6 fields: supplier name, invoice number, date, currency, total, discount, tax, lines[{name, strength, form, pack, quantity, bonus, unitCost, lineTotal, lot, expiry, barcodeText}] each nullable, plus `unclear` notes per line and per header from the model, page per line), Zod re-validation of the output, invoice text only inside `untrusted('invoice', ...)`, no tools offered, <= 200 lines per file (more -> `TOO_MANY_LINES`). A field not visible is `null`; NO completion. Money as integers in minor units of the currency the invoice states (IQD whole dinars, USD cents); a decimal the model cannot give exactly -> null. Quantities are whole numbers of the invoice's pack unit as written. Sorani is not declared supported (Arabic, English and mixed are the supported set at UAT). Cost if wrong: a prompt revision.
- R5-8 Barcodes: the model does NOT read barcodes. GS1 parsing (AI 01 GTIN, 10 lot, 17 expiry YYMMDD) is a pure function applied to barcode TEXT: the review row has a "scan barcode" field (keyboard-wedge scanner of phase 3) and the printed GS1 text if the model transcribed it (`barcodeText`); a valid GS1 string fills lot/expiry only if the row's own lot/expiry are empty and marks the source "from barcode". Image-based barcode decoding (zxing) is NOT built: the spec says to decide it by testing on real photos; recorded as a launch decision. Cost if wrong: one library and a server step later.
- R5-9 Matching (pure, server): exact barcode (to a unit) -> product+unit; else exact identity key (trade name + strength + form + pack, phase-1 normaliser) -> product; else `UNMATCHED` with up to 5 candidates by name similarity (phase-1 search service) for the reviewer. NO automatic merge across strengths or packs: any doubt (two candidates, strength mismatch) -> `AMBIGUOUS` and approval is blocked until the reviewer chooses. A matched row is still shown as editable.
- R5-10 Validation (pure): line total = quantity x unit cost - line discount where all given; sum of lines + tax - discount vs the header total; differences are shown and BLOCK approval until the reviewer acknowledges them with a reason (`MISMATCH_ACKNOWLEDGED`). Derived flags (no numeric confidence): `MISSING` (required for approval and null: product, quantity, lot, expiry; cost may be 0 only with `freeOfCharge`), `MATH_MISMATCH`, `MODEL_UNCLEAR`, `AMBIGUOUS_MATCH`, `EXPIRED`, `DUPLICATE_LINE`. A row with an open flag cannot be approved; the reviewer clears a flag by editing the field, choosing a match, or marking it reviewed with a note (stored).
- R5-11 Approval needs `purchase.manage` only (`ai.use` is for starting an extraction). One transaction: re-validate every row server-side (flags recomputed from stored values, never trusted from the client), refuse on any open flag, refuse a duplicate invoice (fingerprint/number) with the existing invoice named, create the draft receipt via `createDraft` (lines with product, unit, qty, bonus, lot, expiry, cost), link `receiptId` on the batch, status APPROVED; idempotent by `clientKey`. Unconfirmed receipts never move stock.
- R5-12 Outage: any AI failure (timeout, provider error, refusal, unreadable, budget, pricing unset, storage unconfigured) leaves the batch and files, marks the file `FAILED` with a code, and the screen offers "Enter manually" (the ordinary receive screen with supplier prefilled) and "Try again" (same `intakeFileId`: replay-safe, at most one extraction in flight per file via a conditional status update, no double spend). Cost if wrong: none.
- R5-13 Audit and data: `PhIntakeRow` keeps `extracted` (as the model returned after Zod) and `edited` (reviewer values) so before/after is reproducible; `AuditLog` gets ids, counts, status changes, flag codes, token counts and cost, NEVER the image, extracted text, names or numbers of the invoice. `PhAiCall` stores metadata only (purpose, model, tokens, ms, status, cost micro-USD), no prompt or answer. Reviewer notes are stored in the row, not in audit.
- R5-14 Permissions: upload/extract/retry/edit rows = `ai.use` AND `purchase.manage`; viewing a batch = `purchase.manage`; viewing the file image = `purchase.manage` (signed URL minted per request after the access check, 5-minute life, never stored); usage card = `purchase.manage` + `report.view`. Actual matrix (read from `permissions.ts`, not changed): OWNER, BRANCH_MANAGER and PHARMACIST_IN_CHARGE hold both and can start/retry/edit; STOCK and ACCOUNTANT hold `purchase.manage` but NOT `ai.use`, so they can view batches and approve a finished batch but cannot start extractions (owner may widen the matrix later; listed as a decision); PHARMACIST has `ai.use` but not `purchase.manage` (blocked); CASHIER has neither.
- R5-15 UI: screens under `/pharmacy/purchasing/intake/**`: batch list, new batch (choose files or camera `capture` input, supplier optional), batch detail with per-file status (uploaded / rejected with retake reason / extracting / extracted / failed with manual-entry link), review table beside the original (image via signed URL; PDF in an `object` with the page anchor; "page N" per row), flags with icon+text, inline editing with draft kept on the device, match picker (candidates), approve bar (blocked with the reasons listed), usage/budget card. No motion; en/ar/ckb (ar/ckb machine-drafted); RTL; 375/768/1280; axe in EN and AR AND ckb; 44px targets; per-attempt keys; offline state; read-only mode. The hub's "Purchasing" gets an "Invoice by photo" card.
- R5-16 Tests use the fake provider with fixture invoices (a synthetic set of 50 generated invoice images/texts with known truth, in-repo generator, no real data): measured by assertion that (a) every null in the model output stays null in rows (no completion), (b) arithmetic mismatches flag, (c) duplicates are caught, (d) outage -> manual path, (e) budget stops. The real-invoice evaluation is a script + checklist for the owner (`docs/pharmacy/intake-uat.md`).
- R5-17 Tests share ONE database: one DB test file at a time, always `BUZZIFY_DB_PORT=54503`.
